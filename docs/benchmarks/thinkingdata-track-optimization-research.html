ThinkingData 通用 Track 优化调研

调研日期：2026-09-03 · 基线版本：89224ab · P0 修复：cc47e5b · P1：本次提交 · 适用路径：Tracker(THINKINGDATA).Track(fields...)

结论

当前成本来自字段转换、ThinkingData 内层 JSON、Logbus 外层 JSON 与未缓冲写出的串行链路。P0 已回收内层 JSON 的临时内存；P1 已让通用 Track 的标量字段跳过完整中间 map，复杂字段保留原路径。

P0 已完成：cc47e5b 让 ThinkingData 在当前日志写完后立即归还内部临时内存。BI、BigQuery、Elasticsearch 等其他模块拿到的是独立副本，可继续保存和使用。

成本链路

业务 fields ↓ trackLogger.Track ├─ ExtractFields │ ├─ 标量 / Reflect：直接拆分协议字段和 Properties │ └─ Object、Array、Namespace、Error、非法字段等：回退 MapObjectEncoder + ExtractEncoder ├─ Data.WithJSONV2：ThinkingData 内层 JSON └─ PrintThingkingData └─ TrackWithChannel（同步外层 JSON） └─ WithZapJSON 归还内层 buffer

分配采样中，Zap buffer 约占 27.4%，内层 JSON 约占 19.6%，MapObjectEncoder.AddInt64 约占 16.1%，AddString 约占 10.7%，glsEncoder.EncodeEntry 直接占 10.7%（外层临时切片 + 每条 log_xid 构造，累计约 38.7%）。NewMapObjectEncoder 自身仅约 1.8%，所以对象池不是优先项。

为什么 AddInt64 / AddString 合计约 26.8%：MapObjectEncoder 会把基础类型值存进 map[string]interface{}；编译器逃逸分析确认字符串和整数值会逃逸。属性较多的额外成本还包括 map 扩容、字段转换和两层 JSON 编码，不能把 4.4 倍分配次数完全归因为装箱。

默认未缓冲 Pipe 的 CPU 采样中，系统写入调用占 95.4%。这说明写出是独立热点；但本地 Pipe 不能替代 GM15 的 stdout、Fluent Bit 和 Logserver 实测。

问题、代码与解决方案

以下百分比来自“分配字节”采样，不是 CPU 时间比例。常规属性事件总分配为 3,816 B；例如 Zap buffer 的 27.4% 大约是 1 KiB 临时内存。

P0 问题 1：内层 JSON 的 Zap buffer 未归还对象池（已完成）

修复前：生成 JSON 的临时内存没有归还

Zap 的 EncodeEntry 返回来自对象池的 buffer。旧代码取出其中的字节切片后直接返回，但没有调用 buffer.Free()。

修复前代码：utils/zap2json.go（89224ab）

func Zap2Json(data []zap.Field) (bytes []byte, err error) {
    buffer, err := jsonEncoder.EncodeEntry(entry, data)
    if err != nil {
        return
    }
    bytes = buffer.Bytes()
    bytes = bytes[:len(bytes)-len(zapcore.DefaultLineEnding)]
    return
}

修复前的 ThinkingData 调用方式

func (s *StdLogger) PrintThingkingData(data thinkingdata.Data) {
    bytes, err := data.MarshalAsJsonV2()
    if err != nil { /* 记录错误 */ }
    s.TrackWithChannel(THINKINGDATA, zap.ByteString(MsgBody, bytes))
}
ThinkingData 字段 ↓ EncodeEntry Zap buffer ↓ 返回 buffer.Bytes() 切片 MarshalAsJsonV2 / PrintThingkingData 消费字节 ↓ 没有 buffer.Free()，buffer 无法回到 Zap 对象池

旧函数末尾不能直接补 buffer.Free()：函数已经把这块临时内存交给调用方了。若立即归还，下一条日志可能覆盖其中内容，调用方会读到错误数据。

修复后：当前日志写完就归还临时内存

utils.WithZapJSON 将刚生成的 JSON 交给 ThinkingData。当前日志的外层 JSON 写完后，立即归还这块临时内存；之后不会再继续使用它。

修复后代码：utils/zap2json.go:27-40

func WithZapJSON(data []zap.Field, consume func(encoded []byte)) error {
    buffer, err := jsonEncoder.EncodeEntry(entry, data)
    if err != nil {
        if buffer != nil { buffer.Free() }
        return err
    }
    defer buffer.Free()
    encoded := buffer.Bytes()
    encoded = encoded[:len(encoded)-len(zapcore.DefaultLineEnding)]
    consume(encoded)
    return nil
}

修复后的 ThinkingData 调用方式

func (s *StdLogger) PrintThingkingData(data thinkingdata.Data) {
    err := data.WithJSONV2(func(bytes []byte) {
        s.TrackWithChannel(THINKINGDATA, zap.ByteString(MsgBody, bytes))
    })
    if err != nil { /* 记录错误并写空 msg */ }
}
ThinkingData 字段 ↓ WithZapJSON Zap 临时内存 ↓ 当前日志写入完成 外层 JSON 已写出 ↓ buffer.Free() 归还对象池

BI、BigQuery、Elasticsearch 等模块通过 Zap2Json 取得 JSON 时，会先拿到一份独立副本。函数返回后这些模块仍可继续保存和使用该内容；原来的临时内存可以立即回收。ThinkingData 的当前写日志过程不需要这次复制。

编码器会在 JSON 末尾添加换行。代码按照当前换行配置的实际长度去除它；日后调整换行配置时，需要重新运行对应测试确认结果。

三组基准结果见上表。TestZap2JsonReturnedBytesRemainValid 验证其他模块拿到的 JSON 在后续 128 次编码后仍保持正确；TestThinkingDataOutputSurvivesInnerBufferReuse 连续写出 128 条事件并逐条校验 sequence。相关单测与 -race 已通过。

P1 问题 2：通用 Track 为每条日志构造中间 map（已完成）

优化前：全部字段先进入中间 map

旧路径不区分字段用途。账号、事件、类型等 6 个协议字段与业务属性一样，都会先写入 MapObjectEncoder。

优化前代码：track_logger.go（P1 前）

memoryEncoder := zapcore.NewMapObjectEncoder()
for _, field := range fields {
    field.AddTo(memoryEncoder)
}
data, err := thinkingdata.ExtractEncoder(memoryEncoder)
logger.PrintThingkingData(data)
[]zap.Field ↓ 每个字段按 zap.Field.Type 写入 MapObjectEncoder map[字段名]值（包含协议字段和业务属性） ↓ ExtractEncoder 过滤非法字段 → 读取协议字段 → 删除协议字段 ↓ 剩余 map 作为 Data.Properties

因此协议字段会经历“写入 map，再从 map 删除”。基础类型也会在写入 map[string]interface{} 时产生适配和分配成本。

优化后：协议字段直接拆分

trackLogger.Track 现在调用 thinkingdata.ExtractFields(fields)。标量、作为属性的 Reflect 和 Skip 字段先进入轻量路径。

优化后代码：track_logger.go:46 · thinkingdata/extract.go:15、88

data, err := thinkingdata.ExtractFields(fields)
logger.PrintThingkingData(data)
[]zap.Field ↓ ExtractFields 协议字段（账号、类型、事件等）→ 局部变量 业务属性 → Data.Properties ↓ 复用原有 TrackWithType / User 校验和 JSON 编码

这样避免先将协议字段放入 map 再删除；但最终的业务属性仍需保留在 Properties，以维持现有 ThinkingData 数据结构。

兼容边界

Object、Array、Inline、Namespace、Error、Stringer、未知类型和非法字段自动回退原有 MapObjectEncoder → ExtractEncoder 路径，避免改变延迟 marshaler、附加错误字段和嵌套结构。重复 key、#time、#ip、#uuid、#first_check_id 与 USER_ADD 保持原有处理。

验证与收益边界

字段级对照覆盖标量、Reflect、复杂字段回退和错误场景；端到端 JSON 与 -race 通过。常规属性少 7 次分配，属性较多少 11 次。Data.Properties 仍是 map[string]interface{}，业务属性仍须装箱；高频固定事件可继续评估 TrackWithTGAData。

P2 问题 3：属性名可能被正则校验两次

标量快速路径在 thinkingdata/extract.go:97-99 校验字段名；复杂字段的回退路径在 thinkingdata/extract.go:28-32 校验。两条路径保留下来的属性都会在 thinkingdata/utils.go:74-79 由 formatProperties 再校验一次。属性较多时，32 个属性会重复扫描。

方案：保留第一次“静默过滤”的行为，仅为通用路径增加跳过第二次 key 正则校验的内部函数；时间格式化与 USER_ADD 数值校验不能跳过。Go 允许在遍历 map 时删除键；这里没有可依赖的遍历顺序或并发语义。回归用例须覆盖非法 key 与保留字段冲突、事件 ID、时间、UUID、复杂 Field 和重复 key。

P4 问题 4：内层 ThinkingData JSON 又被包成外层 JSON 字符串

stdlogger_itracker_impl.go:10-13 在 WithJSONV2 回调内把内层 JSON 以 zap.ByteString("msg", bytes) 写入外层 Logbus JSON。常规属性从 269 B 内层变为 595 B 外层；引号还会发生转义。

方案：只有 Logserver、Fluent Bit、查询脚本和所有消费者确认 msg 可以从 JSON 字符串改为嵌套对象时，才能改变格式。它是协议变更，未确认前不实施。

P2/P3 问题 5：外层字段构造与未缓冲写出

baisc_encoder.go:14-28 每条日志都会生成 XID、创建临时字段切片并合并全局字段；其直接分配占比约 10.7%。这是所有日志的公共路径，必须先独立基准和兼容性验证。

export_setting.go:47-51 定义了 256 KiB、30 秒刷出的 BufferedWriteSyncer，但默认未启用。GM15 可先以单实例开启 WithBufferedStdout(true)；它只减少写系统调用，不减少 JSON 编码或消息大小。必须验证检索延迟、Fluent Bit 丢弃、SIGTERM 与 Close() 刷出。

P5 低优先级：Tracker 缓存；不建议 MapObjectEncoder 对象池

创建 Tracker 约 64 ns、104 B、4 次分配，只占常规 Track 耗时约 1%；可随业务改动缓存。不要单独池化 MapObjectEncoder：ExtractEncoder 会把它的 map 交给 Data.Properties，过早归还会造成数据串写，复制/清空又会抵消收益。

优化优先级

优先级建议收益依据风险与决策
P0归还内层 JSON 的 Zap buffer（已完成）三组事件分配字节降低 27.7%、85.5%、86.1%。Zap2Json 的 6 个生产调用点都会归还临时内存；ThinkingData 当前写日志时还少一次复制。已完成：ThinkingData 写完一条日志后立即归还内部临时内存。其他模块通过 Zap2Json 取得内容时，会拿到独立副本。BigQuery 处理带业务属性的日志时会生成两段 JSON，两次临时内存都会归还。去除 JSON 末尾换行时按当前换行配置的实际长度计算；日后调整配置需重新运行测试。
P0治理事件量和属性量属性较多单条成本约为常规属性 14 倍；少一条日志会同时减少编码、分配和写出。下一步：由 BI/运营确认字段白名单、采样规则与统计口径，先完成事件与属性盘点。
P1通用 Track 标量字段快速路径（已完成）常规属性少 7 次分配；属性较多少 11 次；并发属性较多吞吐提升约 12%。注意：复杂或非法 zap.Field 回退旧路径；Properties 仍是 map[string]interface{}，不能消除全部属性装箱。
P1高频事件使用类型化 ThinkingData 入口现有 TrackWithTGAData 可进一步跳过通用协议适配。注意：需处理非法键、UUID、时间、重复 key 和复杂 Field 的语义差异。先迁移 1～2 个字段固定的高频事件并做 JSON 对照。
P2通用路径去重字段名校验ExtractEncoder 和 formatProperties 会对保留属性重复做正则校验。遍历 map 时删除非法字段是 Go 允许的写法。不能改变“非法字段静默删除”、保留字段拆分和重复 key 最终值；不依赖遍历顺序或并发语义。回归用例须覆盖非法字段与保留字段（#account_id/#event_id/#time/#uuid/USER_ADD）冲突的组合场景，以及重复 key。
P3GM15 实测 BufferedStdout系统写入在本地采样中占主导，现有配置支持缓冲。注意：缓冲降低 syscall，不降低每条编码成本；须验证 p99 可见性、异常退出丢失和 SIGTERM flush。
P4评估去除双 JSON / 外层字段优化常规属性内层 269 B、外层 595 B；外层 glsEncoder 还生成 XID 和临时字段切片，累计约占分配 38.7%。注意：改变 msg 类型会影响 Logserver、Fluent Bit 和查询链路。日志追踪字段是平台约束，对象池需先证明 Encoder 不保留切片。下游协议未确认前不改。
P5缓存 Tracker可省 64 ns、104 B、4 次分配；耗时上仅约占常规路径 1%，但能减少约 12.5% 的分配次数（4/32）。安全且简单；trackLogger 配置创建后只读，可随业务改动一并处理。

不建议优先做的事

MapObjectEncoder / map 对象池

ExtractEncoder 会将同一个 map 作为 Data.Properties 继续编码。过早回收到池中会带来字段串写或并发问题；复制 map 后再复用也可能抵消收益。

只靠提高并发

并发未线性提升，且不会减少每条日志的内存、编码和下游字节数。

删除 TruncateWriteSyncer

常规长度下仅有一次长度判断，不是热点；删除会失去超大日志保护。

推荐验证顺序

  1. 临时内存回收（已完成）：ThinkingData 写完当前日志后归还临时内存；其他模块通过 Zap2Json 拿到独立副本。后续若引入异步 CoreWrapper，再补充其生命周期验证。
  2. GM15 写出缓冲试验：单实例对照采集 CPU、GC、stdout 字节、Fluent Bit 丢弃、检索延迟与优雅退出尾部完整性。
  3. 事件/属性治理与类型化迁移：统计每个事件的 QPS、属性数、消息字节、消费方；先处理无消费方字段，再迁移少量高频固定字段事件。
  4. 通用路径细节优化：在非法键、保留字段、时间、UUID、USER_ADD、复杂 Field 和重复 key 都有回归用例后，再处理重复校验和外层临时字段。

验收标准与证据边界

  • 同一输入、同一命令运行 5 次，以中位数比较 ns/op、B/op、allocs/op。
  • 通过 TestThinkingDataBaselineOutput 与连续写出用例，外层 Logbus JSON、内层 ThinkingData JSON 和多条事件内容都必须有效。
  • 压测环境确认没有新增日志丢弃，关键事件可检索，改善不以不可接受的日志延迟换取。
  • 8 路常规属性和属性较多路径已通过 -race；race 模式数字不纳入性能基线。

本报告覆盖 logbus 进程内通用路径与本地 Pipe 写出；GM15 实际 QPS、属性分布、stdout 背压、Fluent Bit、Logserver 与下游消费规则仍需在压测环境验证。
